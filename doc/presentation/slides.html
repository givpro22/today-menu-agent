2 · 주요 기능과 시스템 구성

주요 기능

식사 상황을 한 문장으로 적으면 조건에 맞는 메뉴를 최대 3개, 이유와 함께 보여 준다.

문장 → 조건

LLM 이 예산·시간·알레르기·끼니를 뽑고, 표기는 코드가 데이터에 맞춘다. 밀가루는 밀로, 해산물은 새우·오징어·조개·생선으로 바꾼다.

코드 판정

알레르기·맵기·끼니·최근 추천·먹은 메뉴는 rules.py 가 거른다. LLM 이 무엇을 골라도 verify 를 거쳐야 결과에 들어간다.

완화 전에 승인

후보가 없으면 "예산을 8,500원으로 올려서 찾아볼까요?" 처럼 먼저 묻고 기다린다. 알레르기·맵기·끼니는 풀지 않는다.

이유 검증

review 노드가 이유 속 맵기·국물 표현을 메뉴 데이터와 대조하고, 틀리면 데이터로 만든 문장으로 바꾼다. 기본은 규칙 판정이다.

재시작해도 기억

최근 추천 6개와 식사 기록은 session.db, 승인 대기 상태는 checkpoints.db 에 둔다. 서버를 다시 켜도 이어진다.

먹었어요 · 식사 기록

추천 카드의 버튼으로 먹은 메뉴를 남긴다. 최근 3일 안에 먹은 메뉴는 다음 추천에서 뺀다.

3 · 기술적 특징

기술적 특징

판정은 코드가 하고, LLM 은 조건을 뽑고 후보 안에서 고르고 이유를 쓴다.

  • rules.py 의 판정 함수를 filter 와 verify 가 같이 쓴다. 사본을 두지 않았고, 같은 함수인지 테스트로 확인한다
  • build_graph(deps) 로 LLM 과 menu_repo 를 주입한다. fake·openai·ollama, MCP·로컬을 env 로 바꾼다
  • MCP Tool 4개와 Resource 1개(알레르기 사전). MCP 가 응답하지 않으면 로컬 JSON 으로 폴백한다
  • interrupt() 로 멈추고 Command(resume=...) 로 잇는다. 대기 상태는 AsyncSqliteSaver 가 파일에 남긴다
  • 루프 상한을 State 카운터로 둔다. 완화 2회, 재추천 1회
  • 계약 문서(v1.2)를 먼저 쓰고 그래프·백엔드·화면을 나눠 구현했다

4 · 실행과 테스트 결과

실행 화면

5000원·밀 알레르기 문장이면 예산을 얼마로 올릴지 먼저 묻고, 승인하면 그 조건으로 다시 찾는다.

1. 승인 요청 후보가 0개라 5,000원 → 8,500원을 제안한다. 알레르기·맵기·끼니는 바꾸지 않는다.

2. 승인 후 결과 OpenAI 로 돌린 실제 응답. 완화 내역은 코드가 첫 줄에 쓴다.

3. 재방문 직전 추천 3개와 먹었어요를 누른 메뉴를 빼고 추천한다. 서버를 다시 켜도 같다.

5 · 개선 성과와 한계

한계와 다음

안전 조건은 지켰지만, 이유 문장의 질과 응답 속도는 아직 손볼 곳이 남아 있다.

  • LLM 판정 reviewer 가 맞는 이유도 모순이라고 자주 판정했다 1차 실측에서 판정 30건을 직접 읽어 보니 약 25건이 오탐이었다. 기본값을 규칙 판정으로 바꾸고 LLM 판정은 옵션으로 남겼다. 규칙 판정은 표현을 놓칠 수 있다.
  • 이유 문장이 사용자 상황과 약하게 이어진다 돈 없음·밀 알레르기 문장에도 "혼자서 간편하게" 같은 말이 반복된다. review 는 데이터 모순만 보기 때문에 이건 못 잡는다.
  • "어제 치킨" 에서 닭고기 회피가 추출되지 않았다 노트북 추출 규칙 2 가 실모델에서는 지켜지지 않았다. 이번 결과에는 영향이 없었다.
  • LLM 을 동기 httpx 로 호출해서, 응답을 기다리는 동안 서버 전체가 멈춘다 노드에서 asyncio.to_thread 로 감싸면 인터페이스는 그대로 두고 풀 수 있다.
  • 데이터가 틀리면 코드 판정도 같이 틀린다 북엇국(북어)에 생선 표기가 빠져 있던 것을 실측 중에 찾아 고쳤고, 재료 → 알레르기 대응표로 데이터를 검사하는 테스트를 넣었다.
