# 발표 개요 (5분, 슬라이드 9장)

과제 필수 5항목 순서대로 구성했다. 슬라이드마다 위쪽 작은 라벨에 몇 번 항목인지 적는다.
1 주제와 개발 목적 / 2 주요 기능과 시스템 구성 / 3 기술적 특징 / 4 실행과 테스트 결과 / 5 개선 성과와 한계.
시간은 슬라이드 3분 25초 + 시연 1분 30초로 잡았다. 원본은 `doc/presentation/slides.html`, 출력은 `doc/presentation.pdf`. 숫자는 `eval/results/2026-10-22_openai_final_summary.md` 와 `_workspace/05_qa_report.md`, `05_qa_live_runs.md` 에 있는 값만 쓴다.

## 1. 오늘뭐먹지 [1]
- 라벨: AI 서비스 개발 Mini-project · 과제 2 신규 서비스
- 핵심 문장: 노트북에서 만든 메뉴 추천 그래프를 sample 프로젝트 구조 위에서 실제로 쓸 수 있는 서비스로 옮겼다.
- 예시 문장: case3("돈이 없어서 5000원 안쪽으로…") → 조건에 맞는 메뉴 최대 3개와 이유.
- 이름 줄은 아직 넣지 않았다(사용자 확인 중).
- 시간: 10초

## 2. 왜 만들었나 [1]
- 핵심 문장: 점심·저녁 메뉴 고르기는 매일 하는 일인데, 따져야 할 조건이 한꺼번에 붙는다.
- 문제 상황: 예산·시간·알레르기·맵기·끼니를 같이 따져야 한다. 검색·앱 필터는 조건을 하나씩 골라야 하고 알레르기는 메뉴마다 직접 확인해야 한다. 일반 챗봇은 그럴듯하게 답하지만 알레르기 메뉴가 섞여도 막는 장치가 없다.
- 사용자: 점심과 저녁 메뉴를 고르는 직장인과 학생. 조건을 체크박스로 고르지 않고 말로 적는다(노트북 2절 요구사항 분석).
- 개발 목적: 한 문장 → 메뉴 3개와 이유 / 알레르기 메뉴는 어떤 경로로도 내보내지 않음 / 조건을 바꿔야 하면 먼저 묻기 / 지난 추천·먹은 것 기억해서 빼기 / 노트북을 벗어나 브라우저 서비스로.
- 아래 한 줄: 이전 과제 노트북(LangGraph)에서 출발했다. 노트북과 비교한 결과는 8장에 있다.
- 설문·통계 숫자는 쓰지 않는다(없는 근거).
- 시간: 35초

## 3. 주요 기능 [2]
- 핵심 문장: 식사 상황을 한 문장으로 적으면 조건에 맞는 메뉴를 최대 3개, 이유와 함께 보여 준다.
- 카드 6개: 문장 → 조건 / 코드 판정(알레르기·맵기·끼니·최근 추천·먹은 메뉴) / 완화 전에 승인 / 이유 검증(기본 규칙 판정) / 재시작해도 기억(session.db, checkpoints.db) / 먹었어요·식사 기록(최근 3일 제외).
- 시간: 20초

## 4. 시스템 구성 [2]
- 핵심 문장: 화면은 Vue, API 는 FastAPI, 판단은 LangGraph 가 맡는다. 데이터는 MCP 서버와 SQLite 에 있다.
- 그림: 브라우저(web_chat.html) → web_demo_server :8600 → server.py :8100 → LangGraph ↔ MCP 서버(stdio, Tool 4·Resource 1), OpenAI / session.db, checkpoints.db.
- sample 에서 그대로 둔 것(FastAPI·SSE·MCP stdio, 의존성 주입, SQLite 대화 기록)과 바꾼 것(장애 진단 노드·데이터 → 메뉴 추천).
- 시간: 20초

## 5. 기술적 특징 [3]
- 핵심 문장: 판정은 코드가 하고, LLM 은 조건을 뽑고 후보 안에서 고르고 이유를 쓴다.
- 그림: 그래프 노드 12개. approve_relax·review 는 새로, remember 는 State → SQLite 로 바꿈.
- 항목: rules.py 판정 함수를 filter/verify 가 공유(테스트로 같은 함수인지 확인) / build_graph(deps) 로 LLM·menu_repo 주입(fake·openai·ollama, MCP·로컬) / MCP Tool 4개 + Resource 1개, 실패 시 로컬 폴백 / interrupt() + Command(resume) + AsyncSqliteSaver / 루프 상한(완화 2회, 재추천 1회) / 계약 문서(v1.2) 먼저 쓰고 병렬 구현.
- 시간: 30초

## 6. 실행 화면 [4]
- 핵심 문장: 5000원·밀 알레르기 문장이면 예산을 얼마로 올릴지 먼저 묻고, 승인하면 그 조건으로 다시 찾는다.
- 그림: `img/s03_chat.png`(승인 카드), `img/s11_chat.png`(OpenAI 실제 결과), `img/s07_chat.png`(재방문 때 직전 추천·먹은 메뉴 제외). 원본에서 사이드 패널을 뺀 채팅 영역만 잘라 썼다.
- 시연(1분 30초): case3 입력 → 승인 → 카드 → 먹었어요 → 서버 재시작 → 같은 요청 → 직전 메뉴 빠짐. 네트워크가 안 되면 fake 모드와 스크린샷으로 대신한다.

## 7. 테스트 결과 [4]
- 핵심 문장: 개발과 테스트는 fake LLM 으로 돌리고, 실제 OpenAI 는 스모크와 실측에만 썼다.
- 표: pytest 140 passed / 0 failed, 27초(QA 회차 5-R) / 회귀 문장 라이브 fake 22/22(회차 3) / 승인 대기 중 재시작해도 대기 유지 / 같은 승인 두 번이면 두 번째 409 / OpenAI 스모크 4/4, 호출 12회, 폴백 0(회차 4).
- 한 줄: 알레르기 정답은 사람이 적은 표에서 가져온다(시스템 사전과 같이 틀리지 않게).
- 시간: 20초

## 8. Before / After [5]
- 핵심 문장: 같은 21문장을 같은 모델(gpt-4o-mini, temperature 0)로 두 번씩 돌려 채점했다.
- 표(1회차 값, 2회차가 다르면 "a / b"):

| 지표 | Before | After |
|---|---|---|
| 알레르기 위반 메뉴 (단일) | 3 (북엇국 2, 우동 1) | 0 |
| 해산물 문장 알레르기 정규화 누락 | 4 / 4 | 0 / 4 |
| 재시작 후 직전 추천과 겹친 비율 | 0.963 / 0.926 | 0 |

## 9. 한계와 다음 [5]
- 핵심 문장: 안전 조건은 지켰지만, 이유 문장의 질과 응답 속도는 아직 손볼 곳이 남아 있다.
